YOLO Inference Mechanics
for the Nutritional Arbiter

A precise, step-by-step explanation of how the Global and Israeli YOLO11l-cls models ingest images, produce probability distributions, and how the routing labels for the XGBoost Arbiter are derived.

§ 0

System Overview

The Nutritional Arbiter is a meta-learner (XGBoost classifier) that, given a food image, decides which of the two domain experts to trust: the Global model (trained on general food categories) or the Israeli model (fine-tuned on local Israeli cuisine). It does not classify food itself — it routes.

To train the Arbiter we first run both models on every image in the validation and test splits, collect their top-2 predictions and confidence scores, and record which model was actually correct. That truth-label (arbiter_label) is the training target.

Why val + test only? The YOLO models were trained on the train split. Using those same images to generate Arbiter training data would cause label leakage: YOLO confidences on training images are artificially inflated, making them unrepresentative of real-world routing difficulty. The Arbiter must learn from held-out data.
§ 1

Image Preprocessing & Ingestion

When the script calls model(image_path, imgsz=224), the Ultralytics engine executes a deterministic preprocessing pipeline before the image ever reaches the neural network backbone. Each step is mandatory and non-configurable at inference time.

Step 1 — Read & Decode

Ultralytics internally calls cv2.imread() (OpenCV) which reads the raw JPEG/PNG bytes from disk and decodes them into a NumPy array of shape (H, W, 3) in BGR colour order with dtype uint8 (values 0–255). Note the channel order: BGR, not RGB — OpenCV's default.

Step 2 — Letterbox Resize to 224 × 224

Real food images rarely arrive as perfect squares. Ultralytics uses a technique called letterboxing (also called "pad-resize") to handle arbitrary aspect ratios without distorting the content.

🖼
Original
H × W (arbitrary shape)
📐
Scale
Longest edge → 224px (bilinear)
⬛
Pad
Add grey bars to reach 224 × 224
🔢
Normalize
÷ 255 → float32 [0.0, 1.0]
🧠
Backbone
Tensor (1, 3, 224, 224)

The letterbox algorithm computes the scale factor r = 224 / max(H, W) and resizes both dimensions proportionally. The remaining pixels (on the shorter axis) are filled with the constant value (114, 114, 114) — a neutral grey chosen because it lies near the mean of the ImageNet dataset. The padding is split evenly on both sides of the shorter axis.

Critical detail — Letterbox vs. Stretch Do not confuse letterboxing with naive stretching. If a 400 × 200 image is naively stretched to 224 × 224, objects appear horizontally squashed. With letterboxing the image is scaled to 224 × 112, then padded with 56-pixel grey bands top and bottom. The backbone sees an undistorted image, and the padding contributes nothing meaningful to classification because it is a uniform colour.

Step 3 — BGR → RGB Conversion

OpenCV reads images in BGR order, but the YOLO backbone (a CSP-based or ViT-based network) was trained on RGB-ordered tensors (following the PyTorch / torchvision convention). Ultralytics automatically reverses the channel order: img = img[:, :, ::-1].

Step 4 — Normalisation (0–255 → 0.0–1.0)

The uint8 pixel values are cast to float32 and divided by 255.0. This maps the entire dynamic range to the interval [0.0, 1.0]. 

# Conceptual equivalent of what Ultralytics does internally:
img = cv2.imread(image_path)                  # uint8, (H,W,3), BGR
img = letterbox(img, new_shape=224)[0]         # uint8, (224,224,3), BGR
img = img[:, :, ::-1]                         # uint8, (224,224,3), RGB
img = img.astype('float32') / 255.0          # float32, values in [0,1]
tensor = torch.from_numpy(img).permute(2,0,1) # (3,224,224)
tensor = tensor.unsqueeze(0)                  # (1,3,224,224) — batch dim
No per-channel mean subtraction Unlike many torchvision transforms (which subtract ImageNet channel means and divide by channel std), Ultralytics does not apply per-channel standardisation by default. The only normalisation is the global ÷255 step.

Step 5 — Batch Dimension & Device Transfer

The preprocessed tensor is expanded to shape (1, 3, 224, 224) (batch size 1) and moved to the appropriate device (CUDA or CPU). For our script, single-image inference is performed in a loop; there is no explicit batching, which is intentional for simplicity and memory safety across a large dataset.

§ 2

Data Extraction from the Results Object

The call model(image_path, imgsz=224, verbose=False) returns a Python list of ultralytics.engine.results.Results objects — one element per image in the batch. Since we pass a single image, the list always has length 1. 

results = model(str(image_path), imgsz=224, verbose=False)
# results → list[Results], len == 1

result = results[0]           # Results object for our single image

The Results Object — Key Attributes

AttributeTypeDescription
result.probs Probs Wraps the softmax output of the classification head.
result.names dict[int, str] Maps class index (int) → class label (str) for this model's vocabulary.
result.orig_img np.ndarray The original image as loaded (before preprocessing) — not used in this script.
result.path str Filesystem path of the source image.

The Probs Object — Probability Tensor

The Probs object wraps the raw output logits after the final softmax activation layer. The backbone's fully-connected head produces one logit per class; a softmax converts these to a proper probability distribution (all values in [0, 1], sum = 1.0).

AttributeTypeDescription
probs.data torch.Tensor (N,) Full probability distribution over all N classes, sorted by class index.
probs.top1 int Index of the highest-probability class (argmax).
probs.top1conf torch.Tensor scalar Confidence score of the top-1 class as a 0-dim tensor.
probs.top5 list[int] Indices of the 5 highest-probability classes, sorted descending.
probs.top5conf torch.Tensor (5,) Confidence scores corresponding to top5 indices.

How the Script Extracts Top-1 and Top-2

Rather than using probs.top1 and then separately computing the second-best index, the script uses probs.top5 — a pre-sorted list — to retrieve both positions with a single attribute access each: 

probs  = results[0].probs          # Probs object
names  = results[0].names          # {int: str}

top5_indices = probs.top5          # [idx0, idx1, idx2, idx3, idx4]  ← sorted by conf ↓
top5_confs   = probs.top5conf      # tensor([c0, c1, c2, c3, c4])

# ── Top-1 ──────────────────────────────────────────────────────────────
top1_idx  = top5_indices[0]       # int index of best class
top1_conf = float(top5_confs[0])  # Python float, e.g. 0.8734
top1_cls  = names[top1_idx]        # e.g. "pizza"

# ── Top-2 ──────────────────────────────────────────────────────────────
top2_idx  = top5_indices[1]
top2_conf = float(top5_confs[1])
top2_cls  = names[top2_idx]        # e.g. "flatbread"
Why use top5 instead of top1 + argmax? probs.top5 is already computed and cached inside the Results object after the forward pass. Using it for both top-1 and top-2 avoids redundant tensor sorting and keeps the extraction path clean. The confidence gap between top-1 and top-2 (top1_conf − top2_conf) is itself an informative feature that can optionally be added to the XGBoost input — a large gap signals high model certainty; a small gap signals ambiguity.

Vocabulary Mismatch — A Critical Consideration

The Global and Israeli models were trained on different datasets and therefore have different class vocabularies. The names dict for each model is independent. When the script compares top1_cls against ground_truth_class (the folder name from the dataset), the comparison is made case-insensitively and with whitespace stripping to tolerate naming inconsistencies (e.g. "Bourekas_Cheese" vs. "bourekas_cheese").

Implication for XGBoost features The XGBoost router does not receive raw class strings as features — it receives numeric confidence scores. String class names only matter for computing the binary "was the model correct?" signals used to derive arbiter_label.
§ 3

The Target Variable — arbiter_label

The arbiter_label column is the training target for the XGBoost Arbiter. It encodes which of the four possible correctness outcomes occurred for each image, using the top-1 predictions of both models.

0
Only Global Correct
Global model's top-1 prediction matches the ground-truth folder name. Israeli model's top-1 does not.
→ Route this image class to the Global model.
1
Only Israeli Correct
Israeli model's top-1 prediction matches the ground truth. Global model's top-1 does not.
→ Route this image class to the Israeli model.
2
Both Correct
Both top-1 predictions match the ground truth.
→ Either model can serve; route by highest confidence at inference time.
3
Neither Correct
Both top-1 predictions miss the ground truth.
→ Represents the irreducible error floor. Can be used to trigger a fallback or uncertainty flag.

Python Implementation

def compute_arbiter_label(gt: str, g_top1: str, l_top1: str) -> int:
    gt_norm   = gt.strip().lower()
    g_correct = (g_top1.strip().lower() == gt_norm)
    l_correct = (l_top1.strip().lower() == gt_norm)

    if   g_correct and not l_correct: return 0  # Only Global
    elif l_correct and not g_correct: return 1  # Only Israeli
    elif g_correct and     l_correct: return 2  # Both
    else:                              return 3  # Neither

Why This Label Design Matters

A naïve Arbiter design might binary-label each image as "Global wins" or "Israeli wins" and discard ties or failures. This four-class encoding is superior for three reasons:

  • Preserves signal for ambiguous cases (label 2). When both models are correct, XGBoost can learn the confidence pattern associated with "safe" predictions and route to whichever model is more certain at runtime.
  • Makes failure modes explicit (label 3). Neither-correct rows reveal the joint blind spots of both models. At inference time the Arbiter can predict label 3 with high probability as a confidence abstention signal, prompting a human review or a third fallback model.
  • Enables weighted training. Labels 0 and 1 are the operationally critical classes (the Arbiter must choose the right expert). Labels 2 and 3 are less decision- critical and can be down-weighted in XGBoost's sample_weight parameter if desired.
XGBoost sees numeric features, not class strings The actual XGBoost features are the four confidence scores (global_top1_conf, global_top2_conf, local_top1_conf, local_top2_conf) plus any engineered features derived from them (confidence gap, ratio, etc.). The class names are recorded in the CSV for human interpretability and error analysis, but are not fed to XGBoost directly.

Output CSV Schema

Column Dtype Description
image_path str Absolute filesystem path to the source image.
split_type str "val" or "test" — indicates which held-out split the image came from.
ground_truth_class str True class label, taken verbatim from the parent directory name.
global_top1_class str Global model's highest-confidence predicted class name.
global_top1_conf float Softmax confidence of global_top1_class. Range: [0.0, 1.0].
global_top2_class str Global model's second-highest-confidence class name.
global_top2_conf float Softmax confidence of global_top2_class. Range: [0.0, 1.0].
local_top1_class str Israeli model's highest-confidence predicted class name.
local_top1_conf float Softmax confidence of local_top1_class. Range: [0.0, 1.0].
local_top2_class str Israeli model's second-highest-confidence class name.
local_top2_conf float Softmax confidence of local_top2_class. Range: [0.0, 1.0].
arbiter_label int {0,1,2,3} XGBoost training target. 0=Global only, 1=Israeli only, 2=Both, 3=Neither.
Suggested Engineered Features for XGBoost Consider adding these derived columns before training:
  • global_conf_gap = global_top1_conf − global_top2_conf (model certainty)
  • local_conf_gap = local_top1_conf − local_top2_conf
  • conf_delta = global_top1_conf − local_top1_conf (relative dominance)
  • global_entropy = −Σ p·log(p) over top-5 (optional, requires storing more probs)
